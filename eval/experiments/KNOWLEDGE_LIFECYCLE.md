# 知识生命周期：本地配对实验

测量日期：2026-11-21。原始记录见 [knowledge_lifecycle.json](knowledge_lifecycle.json)，包含 30 次构建观测、完整证据签名、数据文件 SHA-256、环境和配对序号。

## 问题与实验口径

在同一份上游 39 篇政策文档上，对比当前同一管线的 `reload(force=True)` 全量构建和 `reload()` 增量构建。基线并非运行未修改的上游程序；两种模式共用解析、去重和索引发布代码，只切换解析/Embedding 的复用策略。

初始知识库为 127 个去重 chunk。每个场景使用临时目录，先构建相同初始索引并预热同一条查询缓存，再执行确定性的文件更新。原始知识文件不会被改动。每种场景各 3 个配对，交替运行顺序，计时包含扫描、解析/复用、去重、Embedding、BM25、内存索引和发布，不含此前启动构建及之后的检索。

使用 Python 3.12.10、Windows、`HashEmbeddingProvider(dim=32)`，无需 API Key 或模型权重。完整包版本和数据摘要保留在 JSON 中。本地环境通过 pyproject 声明解析安装依赖，没有声称按上游 uv.lock 完全复现。

## 结果

| 场景 | 文档数 | 最终 chunk | 全量向量化文本 | 增量向量化文本 | 全量 P50 ms | 增量 P50 ms |
|---|---:|---:|---:|---:|---:|---:|
| 未变化 | 39 | 127 | 127 | 0 | 106.44 | 13.85 |
| 原文档新增条款 | 39 | 128 | 128 | 1 | 105.82 | 85.38 |
| 新增文档 | 40 | 128 | 128 | 1 | 105.73 | 84.85 |
| 删除文档 | 38 | 122 | 122 | 0 | 100.99 | 80.72 |
| 缩短文档 | 39 | 123 | 123 | 1 | 101.25 | 80.50 |

新增一个条款时，向量化输入从 128 条降到 1 条，减少 99.22%。这是文本条数，不是 API 请求次数、Token、费用或端到端延迟。128 条文本可能在一次批量请求中完成。

5 个场景的 15 个配对中，全量和增量输出的 `(chunk_id, content_sha256)` 集合及知识版本全部相同；删除场景额外检查已删文档不存在。每次检索都会校验返回证据的版本。这里测的是小型离线集合上的索引正确性，不是统计意义上的真实问题回答成功率。

## 结果说明与限制

无变化时可以跳过索引构建；有变化时仍需全量去重和重建 BM25，因此减少 Embedding 输入不一定带来同等比例的整体提速。HashEmbedding 本身很便宜，不能把本表的耗时当成 BGE 或远程 Embedding 的延迟，更不能声称线上成本下降 99.22%。只有 3 次配对，没有做显著性检验或长时间负载压测。

新增回归测试还覆盖失败保留旧索引、文档缩短、旧查询迟到写缓存、多跳版本固定和管理 API 的引用来源；Redis/Qdrant 使用替身，真实服务集成验证仍待做。

## 复现

从项目根目录，在 Python 3.11+ 且已安装依赖的环境执行：

```powershell
python -m eval.knowledge_lifecycle --repeats 3
python -m pytest -q tests/integration/test_knowledge_snapshots.py tests/e2e/test_knowledge_api.py
```

默认重写 JSON。机器负载和包版本变化会影响时间；文本数量、证据集合与删除不残留应保持一致。脚本在不一致时以断言失败退出。
