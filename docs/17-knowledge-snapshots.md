# 知识快照：增量构建与问答一致性

知识生命周期管理围绕一个可验证的问题展开：**知识文件增删改后，能否减少重复向量化，同时保证新请求只读到新证据，进行中的多跳请求继续使用一致的旧证据？**

## 构建与发布

`KnowledgeRuntime.reload()` 在单个进程内串行处理发布请求。

1. 对目录中支持的文件计算 SHA-256，与上次成功发布的清单比较，报告 added / modified / deleted。
2. 复用未变文件的解析结果；对新文件和修改文件重新解析。仍按上游逻辑做精确内容去重。
3. 以清洗后的内容 SHA-256 复用同一 Embedding Provider 的已有向量，只调用模型计算缺失文本。标题修改而正文不变时可以复用向量；切块变化则逐块判断。
4. 在旁路构建完整的新 BM25 与向量索引，重新装配全部有效记录，因此文件删除和文档缩短都不会残留旧 chunk。
5. Qdrant 使用独立版本集合；构建失败不替换当前索引。首次启动仍保留上游的内存降级行为。
6. 再次扫描文件清单，拒绝构建途中变化的候选结果。最后在没有 `await` 的边界替换索引 bundle，再提交新的复用缓存。

版本是文件清单与固定的模型/解析配置的摘要。Provider 实例在 Runtime 生命周期内固定；更换模型需要重建 Runtime。该版本表示内容快照，不表示商品政策的业务生效日期。

这里的“增量”主要减少解析和 Embedding 工作：文件哈希扫描、去重、BM25 构建及新向量集合写入仍处理全量有效数据。它不是所有环节都做到 O(变更量) 的索引系统。

## 查询与缓存

`HybridRetriever` 持有一个包含 BM25、VectorRetriever、Cache 和版本的快照引用。`retrieve()` 在首次等待前取得该引用，整个调用都使用同一份 bundle。即使旧查询在发布后才写入缓存，也只写入旧版本的缓存空间。

普通问答的 `_invoke()` 和 SSE 的 `_run_graph()` 使用 `pin_snapshot()`。它通过 `ContextVar` 让一次图执行中的查询改写、多跳检索和工具检索共享快照；上下文结束或异常时恢复。更新期间的旧请求可以完成，新请求使用新快照。这里不承诺更新后立即中止所有旧请求。

Redis 缓存键包含版本摘要；内存缓存独立于每个 bundle，并在读写时复制 chunk。新增的引用字段：

```json
{
  "chunk_id": "return_policy_..._00",
  "knowledge_version": "<64 位快照 SHA-256>",
  "content_sha256": "<64 位清洗后正文 SHA-256>"
}
```

`chunk_id` 仍沿用上游路径加序号的稳定标识，内容变化后可能不变。必须结合快照和正文摘要识别证据。这些字段提供溯源信息，尚未实现历史正文归档或按旧版本回放接口。

## API 与演示

从项目根目录启动：

```powershell
.\scripts\demo-local.ps1
```

在另一个 PowerShell 中查看状态和发布目录中的修改：

```powershell
Invoke-RestMethod http://127.0.0.1:8002/api/v1/admin/knowledge
Invoke-RestMethod -Method Post http://127.0.0.1:8002/api/v1/admin/knowledge/reload
```

接口复用上游 `require_admin`：配置 `ADMIN_API_TOKEN` 时携带 `x-admin-token`；production 未配置 token 则关闭管理接口。接口不接受任意路径或上传文件；只重读服务端已配置目录。

`POST .../reload?force=true` 用于全量对照；目录被清空时默认拒绝发布，确实要清空可显式传 `allow_empty=true`。目录不存在与空目录分开处理，避免把挂载故障当成删除所有知识。

响应包含版本、变更文件、文档数、chunk 数、解析文件数、实际向量化文本数、复用文本数和耗时。无变化时返回本次 no-op 报告；`GET` 始终返回上次成功发布的报告。

## 验证与边界

新增测试验证增删改、缩短文档、幂等更新、Embedding 异常/错误维度/NaN、解析空结果、空目录保护、构建期间文件变化、并发读写、多跳快照、缓存隔离，以及管理接口和对话引用。Redis 和 Qdrant 部分使用本地替身验证协议逻辑，尚未做真实服务集成压测。

当前边界：

- 复用缓存仅在当前进程存活，重启后重新构建；没有跨进程锁、广播发布或多实例版本屏障。
- 知识内容、历史缓存和旧请求都可能同时驻留内存；大库需要内存预算。Qdrant 旧版本集合没有自动 GC，生产使用前需增加保留策略。
- 两次扫描能发现通常的并发文件修改，但不提供文件系统事务；管理员应先完成写文件，再触发发布。构建期间不得原地改写 Qdrant 已发布集合。
- Provider 的模型名相同而远端权重被替换时无法自动识别；需要固定模型修订版本并重建 Runtime。
- 仍存在上游的用户身份未认证等限制，见 [12-limitations.md](12-limitations.md)。面向真实用户部署前仍需补齐这些能力。
- HashEmbedding 实验只验证计算量和证据一致性，不能得出语义检索准确率、真实模型加速比或幻觉率结论。

实验入口：`python -m eval.knowledge_lifecycle --repeats 3`；结果与原始记录见 [本地报告](../eval/experiments/KNOWLEDGE_LIFECYCLE.md)。
