# 澄清、引用与版本对照

本文记录 0.1 版本的 P0 设计与冻结实验。对话槽位仍在当前版本使用；图节点、忠实度检查和旧规划链已经退役，当前实现见 [请求运行时](23-runtime.md)。复现旧快照前安装 `python -m pip install -e ".[dev,legacy-eval]"`。

## 对话状态

`dialogue_states` 按会话保存待处理操作、候选订单、已选择订单、原因和阶段。阶段为 `idle`、`awaiting_order` 或 `awaiting_selection`。更新与本次聊天记录使用同一个数据库事务；会话归属仍通过现有 SessionRepository 校验。

涉及多笔订单且没有明确选择时，系统先追问，不把第一个匹配到的订单直接交给执行工具。用户补充单一编号后，系统结合已保存的操作形成新的待审核提议。咨询会清除未完成的操作意图，同时保留明确提及的订单，支持后续用户明确申请时继续处理。

模型规划使用解析后的请求，聊天记录保留用户原始输入。订单参数仍要经过格式、用户消息来源、归属、状态及确认复核，澄清状态不会绕过这些检查。纯咨询和缺字段对话仍不建立售后工单。

新表迁移为 `0004`。SQLite 本地启动的 `create_all` 可以增加新表；由 Alembic 管理的数据库执行 `alembic upgrade head`。迁移测试只在临时数据库里升级和降级。

## 政策引用

知识工具返回可追溯的完整片段，包括 document_id、chunk_id、正文摘要和知识版本；不把本机来源路径放入模型工具消息。执行节点把政策工具得到的片段并入本次回答证据，生成与忠实度检查共享这批证据。

政策候选按问题主题、标题和章节排序。离线咨询优先展示政策片段；模型回答缺少有效片段引用时，替换成有来源的原文节选，而不是给原来的无依据回答补一个引用。

该处理保证引用能够追溯，不代表已完成每句话的语义蕴含验证、法律适用判断或自动政策裁决。

## 冻结材料

- `eval/baselines/pre_p0.zip`：修复前的现有系统，包含原有确认、事务、幂等和工单保护，并非删掉保护的弱化基线。
- `eval/baselines/p0_candidate_v1.zip`：首次封存对照使用的候选应用代码，便于保留之后补修前的真实结果。
- `eval/dataset/p0_sealed.jsonl`：32 条、8 个任务族，每族 4 条新多轮场景。
- `eval/dataset/p0_protocol.json`：数据与基线摘要、在线样本 ID、重复次数、请求上限和指标定义。
- `eval/dataset/p0_oracle_lock.json`：首次评测前冻结的裁判及运行器摘要。

场景由开发者编写并预注册，不能称为独立第三方盲测。新数据没有复用旧 100 条任务的原句，重点覆盖澄清、咨询后申请、延后提供编号和再次选择订单；它的分布不能代表真实客服流量。首次运行后，已观察到的场景只能继续作为开发或回归材料。

## 公平对照与判分

两版本使用同一模型配置、相同合成订单与政策、BM25 + Hash Embedding、词项精排及运行限制。政策主题排序和证据传递是本次改动的一部分；对照衡量本次组合改动，不把收益单独归因于某一个模块。

每个对话轮次后关闭并重建应用容器，保留相同临时数据库，检查状态是否依赖进程内存。基础系统与候选系统通过不同子进程加载，避免 Python 模块缓存混用。每个 worker 记录实际应用源码摘要、模型配置、语料摘要及原始调用。

判分直接检查订单、退款、退货和审计记录，不调用应用的 `verify_operation`。咨询引用需解析到已发布语料的 chunk_id，并匹配正文摘要和知识版本；澄清检查没有提议或工单，并满足追问关键词。这些结构检查不覆盖完整语义质量；当前尚无独立人工标注或人工一致性评估。

评测器会在临时合成数据库中确认每个实际提议，包括错误工具或错误订单的提议。分别记录错误提议和实际错误执行：被状态校验拦下的错误提议不会计作错误执行。另有故障注入测试，确保裁判确实能检测到“咨询却被取消订单”的真实数据库变化。

## 运行与预算

```powershell
python -m eval.p0_compare --mode offline --output eval/runs/p0-offline-new
python -m eval.p0_compare --mode online --max-calls 240 --output eval/runs/p0-online-new
```

输出目录必须不存在，旧结果不会覆盖。离线运行全 32 条，每版 3 轮；在线预先选择每个任务族的第 1 条，各计划 3 轮。每轮交替先运行哪一个版本，以减少固定运行顺序的影响。在线上限是整轮跨进程的 HTTP 尝试数，包含重试。预算耗尽后停止；未运行任务不能算失败或从报告中隐藏，必须同时报告计划数、已尝试数和完整配对数。

离线重复用于检验可复现性，不能当作独立统计样本。在线多次结果也有相关性；报告只作描述性对照，不声称统计显著性。原有的 100 条任务已经用于修复，另列为开发回归，不能与新封存集混为一个总准确率。

默认比较的是当前源码。重放首次候选版本时，应在独立目录解压 `p0_candidate_v1.zip`，将其置于子进程 `sys.path` 首位，再调用 `eval.p0_runner`；原始 worker 参数、源码摘要和输入数据均保留在实验材料里。不要把历史候选的成绩当作后来改动版本的重新测量。

可用快照重放入口自动创建隔离目录并校验裁判：

```powershell
python -m eval.replay_p0 --snapshot eval/baselines/pre_p0.zip --variant baseline --mode offline --repeat 0 --output eval/runs/replay-baseline-r0
python -m eval.replay_p0 --snapshot eval/baselines/p0_candidate_v1.zip --variant full --mode offline --repeat 0 --output eval/runs/replay-candidate-r0
```

指定 `--mode online` 才会调用模型 API，单次重放有独立的 `--max-calls` 上限；它不属于已结束实验的累计预算。
